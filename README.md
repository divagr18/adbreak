AdBreak turns the broadcast delivery chain and ad-insertion pipeline into an observable revenue protection runtime for live media networks.

The fundamental problem: broadcast monitoring is built for video delivery, not ad monetization. Network operations centers (NOCs) monitor availability - HTTP 200 responses, segment download latency, and player buffer health. But television and live OTT streaming monetize on ad impressions: SCTE-35 splice cues, dynamic ad decisioning (VAST), SSAI manifest manipulation, and client tracking beacons.

When an ad decision server returns empty pods, a stitcher encounters a transcode profile mismatch, or a client firmware update silently drops tracking beacons, **traditional CDN and playout monitoring stays 100% green while ad revenue collapses to zero.** The stream never buffers, but the broadcaster earns nothing.

AdBreak introduces **Revenue Realization Rate (RRR)** as its primary Service Level Objective (SLO):

$$\text{RRR} = \frac{\text{Confirmed Ad Revenue}}{\text{Expected Ad Revenue}}$$

Operating across Google Cloud Vertex AI and Grafana Cloud via the **official Grafana Model Context Protocol (MCP) server**, AdBreak isolates the broken hop in the delivery chain using runtime PromQL queries, falsifies alternative hypotheses, and executes policy-gated, deterministic runbooks with telemetry verification and human-in-the-loop controls.

## The Ad-Insertion Reliability Matrix

Modern broadcast and FAST (Free Ad-Supported Streaming TV) infrastructure consists of uncoordinated multi-vendor stages:

| Stage | Signals & Telemetry | Silent Failure Mode | Observability Source |
| :--- | :--- | :--- | :--- |
| **Playout Automation** | SCTE-35 binary cues on cue bus | Dropped splice insert cue; corrupted splice descriptors | Redis cue bus metrics |
| **Packager & Origin** | `EXT-X-DATERANGE` & `CUE-OUT` tags | Timestamp drift; missing segment discontinuity tags | Origin packager logs |
| **Ad Decision Server (ADS)** | VAST 4.0 XML ad pods | Empty ad pods; server response timeouts; exhausted inventory | ADS response latency & fill metrics |
| **SSAI Engine** | Manifest manipulation; 1:1 segment stitching | Transcode profile mismatch; audio codec desync; segment 404s | SSAI stitch metrics and structured logs |
| **CDN Edge Tier** | Cache hit ratio; HTTP status codes; TTFB | Edge caching of personalized manifests; stale CORS headers | CDN edge delivery counters |
| **Client Players** | IAB tracking beacons (`start`, `midpoint`, `complete`) | Beacon blackholing on specific OS/firmware; ad-blocker drop | Beacon collector access logs |
| **Financial Ledger** | Deduplicated confirmed impressions | Delayed reconciliation; under-delivery clawbacks | Mimir / Prometheus billing counters |

## Human-in-the-Loop (HITL) as an Operational Primitive

AdBreak treats operator approval as part of the control loop:

* **Blast-radius policy tiers (T0 to T3):** A deterministic policy function classifies every plan. T0 and T1 actions may run automatically when their preconditions hold. T2 actions wait for a person. T3 actions are blocked during a live event or require approval outside event mode.
* **Non-blocking approval:** A held plan appears on the Live Trace UI while the stream keeps playing.
* **Fresh precondition checks:** When an operator approves a plan, AdBreak measures its runbook preconditions again. If the plant has recovered or changed, the stale plan is refused.
* **Telemetry-backed rollback:** A runbook succeeds only when billable impressions recover. If verification fails, AdBreak rolls the change back and records the result in Grafana.

## Two Demonstrated Workflows

### 1. Device-Class Beacon Blackhole & Automatic Repair (Tier 1)

1. **Detection & Blast Radius:** A scheduled polling tick detects a large impression gap for Roku devices while web and mobile clients monetize normally.
2. **Correlation & Signal Isolation:** The agent compares two evidence branches:
   * *Upstream Branch:* Verifies that SCTE-35 cues, packager tags, and ad decision fill rates for Roku sessions are healthy.
   * *Downstream Branch:* Compares CDN delivery and impression metrics, pinpointing that Roku devices are downloading ad video segments but their tracking beacons are being blocked at the edge.
3. **Hypothesis & Counter-Falsification:** The agent identifies a device-scoped beacon blackhole and verifies that Roku video segment requests remain healthy, ruling out a delivery outage.
4. **Automatic Remediation:** The agent maps the diagnosis to pre-approved runbook `rb-beacon-fallback`. Because this change affects only Roku clients, it qualifies as Tier 1 and runs automatically, instructing the SSAI engine to switch Roku clients to server-side beacon reporting.
5. **Telemetry Verification:** The agent samples Prometheus impression counters over the subsequent avail cycle, confirms that billable impressions return to parity, and writes an auditable postmortem.

### 2. Ad Server Exhaustion & Human-in-the-Loop Approval (Tier 2)

1. **Multi-Source Incident:** The live ad decision server runs out of targeted inventory during a peak live event, returning empty VAST pods across all connected viewers in a major region.
2. **Hypothesis & Runbook Lookup:** The agent correlates empty VAST payloads with zero impression creation across all device classes. It identifies `rb-ads-failover` (serving cached fallback house inventory) as the matching remediation.
3. **Policy Gate Halt:** Because serving fallback inventory changes the ad creative for 100% of viewers in that region, the blast-radius policy engine assigns it Tier 2. The agent halts execution, displays the complete evidence bundle on the Trace UI, and requests human sign-off.
4. **Stale Check & Execution:** The operator inspects the live metrics and clicks **Approve**. AdBreak re-checks live ADS fill rates to verify the primary server is still failing. Upon confirmation, the agent activates the fallback ad cache and verifies revenue stabilization.

## Why Grafana MCP

AdBreak uses the official Grafana MCP server, `grafana/mcp-grafana`, as the agent's runtime interface to operational telemetry:

* **Prometheus through MCP:** `query_prometheus` reads revenue, delivery, and agent metrics.
* **Audit write-back through MCP:** `create_annotation` records plans and outcomes in Grafana. `create_incident` creates an incident when Grafana IRM is available.
* **Traceable execution:** Every query and result is preserved in the Live Trace UI beside the reasoning step that used it.

The local polling trigger reads Grafana's alert API because a hosted Grafana instance cannot call a laptop. Diagnosis, verification, and audit write-back use MCP.

## How the Agent & MCP Are Implemented

AdBreak runs a nine-stage control loop:

```text
detect → triage → correlate (2 parallel branches) → hypothesize → falsify → plan → act → verify → document
```

1. **`detect` (code):** Confirms that the revenue gap is still present before opening a run.
2. **`triage` (Gemini):** Measures the affected device class, region, and CDN.
3. **`correlate` (parallel Gemini calls):** Compares the upstream signal chain with downstream delivery and beacon evidence.
4. **`hypothesize` (Gemini):** Selects a root-cause class from the fixed failure taxonomy.
5. **`falsify` (Gemini plus fresh MCP queries):** Tries to disprove that hypothesis with live counter-evidence.
6. **`plan` (code):** Maps the failure class to a versioned runbook or escalates when no safe runbook exists.
7. **`act` (code):** Applies the blast-radius gate. T1 may execute; T2 waits for operator approval.
8. **`verify` (code):** Measures billing recovery over later ad breaks and rolls back if recovery does not appear.
9. **`document` (Gemini):** Produces a technical postmortem and a plain-language financial brief.

Only the reasoning stages use Gemini. Runbook selection, policy checks, execution, verification, rollback, and watchdog enforcement are deterministic.

### Grafana MCP Tools Used at Runtime

| MCP tool | Used for |
| :--- | :--- |
| `query_prometheus` | Detection evidence, correlation, preconditions, and recovery verification |
| `create_annotation` | Plans, holds, remediations, rollbacks, and escalations |
| `create_incident` | Incident creation when Grafana IRM is enabled |

## Broadcast Plant & Google Cloud Architecture

* **Fourteen-service Compose stack:** Nine TypeScript services model playout, packaging, ad decisions, SSAI, edge delivery, players, beacon collection, fault injection, and the agent. Redis, nginx, ffmpeg, Grafana MCP, and Grafana Alloy complete the stack.
* **Real media signals:** Playout emits binary SCTE-35 cues through Redis. The packager adds `EXT-X-DATERANGE` and `CUE-OUT` tags. SSAI builds personalized manifests with one-for-one segment substitution. Two hundred synthetic players fire six IAB tracking events per creative.
* **Google Agent Development Kit:** The agent invokes Gemini on Vertex AI through `@google/adk`. Gemini 3.7 Flash handles fast classification and correlation, while Gemini 3.1 Pro Preview handles deeper hypothesis, falsification, and documentation steps. The GCE deployment provisions a service account with `roles/aiplatform.user` and uses attached credentials rather than a key file.
* **Grafana Cloud telemetry:** Alloy scrapes Prometheus metrics and ships structured logs. The services export OpenTelemetry spans to Grafana Cloud over OTLP. Trace context travels from the cue bus into the manifest and beacon URLs.

## Scope Decisions & Operational Guardrails

* **Reverse Proxy CDN:** The edge tier is implemented as a lightweight TypeScript reverse proxy with custom fault-injection rules rather than a heavy multi-cluster Envoy mesh.
* **Pre-conditioned Video Creatives:** Ad video segments are pre-conditioned to match content stream encoding profiles rather than running multi-bitrate live transcode clusters on demand.
* **Single plant telemetry domain:** `deploy/judging-mode.sh` ensures only one plant ships into the active Grafana telemetry namespace while the agent is being judged.
